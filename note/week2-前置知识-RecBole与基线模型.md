## 0. 衔接：第一周产出了什么，缺的是什么

第一周的 7 个产出物，各自有明确的下游用途：

| 文件 | 谁用 | 什么时候用 |
|---|---|---|
| `train.jsonl` | 训练模型 | 第 5 周（生成式） |
| `valid.jsonl` / `test.jsonl` | 评测 | 全程 |
| `ml-1m.inter` | **RecBole 基线（本周）** | 第 2 周 |
| `item_text.json` | **文本编码器的输入**（编码成 768 维向量后，那个向量才进 RQ-VAE） | 第 3 周 |
| `user_id_map.json` / `item_id_map.json` | 把预测结果翻译回真实 ID | 全程 |
| `preprocess_log.json` | 实验记录 | 结项报告 |

缺的那一环是**模型 + 评测循环**。本周用 RecBole 提供的现成实现补上。

### 0.1 关键区别：`train.jsonl` 是「压缩」的，训练要「展开」的

`train.jsonl` 每个用户**一行**（下面是 user 0 的真实数据，51 个 id）：

```json
{"user": 0, "items": [2757, 861, 1068, ..., 1992, 1314]}
```

但模型训练需要的是**逐条样本**，每条样本 = 一个前缀 + 下一个物品：

```
样本 1 ：输入 [2757]                     → 标签 861
样本 2 ：输入 [2757, 861]                → 标签 1068
...
样本 50：输入 [2757, 861, ..., 1992]     → 标签 1314
```

**user 0 一个人 → 50 条训练样本（= 51 − 1）。**

规律：**每条交互产生一条样本，只有该用户的第一个物品不产生样本**（它前面没有历史）。
所以全库样本数 = 训练交互数 − 用户数 = `987531 − 6040 = 981491`。

> 这个「n − 1」不是推测，两处证据：
> ① RecBole 官方文档给了一个「5 个物品 + `MAX_ITEM_LIST_LENGTH=3` → 展开出 4 条样本」的例子；
> ② 源码 `SequentialDataset.data_augmentation()` 里 `if last_uid != uid: seq_start = i` 这个分支**不产生样本**，
> 只有 `else` 分支才 append —— 也就是从第二个物品才开始建样本。

这就是为什么 RecBole 读的是 `.inter` 而不是 `train.jsonl`：`.inter` 保留了每条交互的原始顺序和时间戳，RecBole 自己负责展开成前缀样本。

> ✅ **跑通后的自查**：一个 epoch 的 batch 数应该约等于 `981491 / 2048 ≈ 480`。如果差得远，说明数据或配置有问题。

## 1. RecBole 是什么

### 1.1 定义

**RecBole 是一个 Python 推荐系统算法库**，把「做一次推荐实验」中**与具体模型无关**的部分全部实现好了：

读数据 → 按协议切分 → 展开成序列样本 → 分批 → 训练循环 → 反向传播 → 早停 → 评测指标 → 日志落盘。

**它不是一个模型，是一个跑模型的框架。** 你只需要提供三样东西：

1. 数据文件（`{data_path}/{dataset}/{dataset}.inter`）
2. 一个配置文件（yaml）
3. 一个模型名字（`SASRec` / `GRU4Rec` / …）

版本：`pip show recbole` 查看，当前是 1.2.x。内置 90+ 个推荐模型。

### 1.2 六个组件（每个对应一段你本来要自己写的代码）

| 组件 | 职责 | 你本来要自己写的 |
|---|---|---|
| **Config** | 读 yaml，按 4 层优先级合并默认值 | 参数管理 |
| **Dataset** | 读 `.inter`、过滤、切分、展开序列 | 数据加载 + 切分 + 样本构造 |
| **DataLoader** | 分批、按 seed 打乱 | `torch.utils.data.DataLoader` 那套 |
| **Model** | 网络结构（SASRec / GRU4Rec / …） | 模型定义 |
| **Trainer** | 训练循环、反向传播、早停、checkpoint | `for epoch: for batch: loss.backward()` |
| **Evaluator** | 全量排序、算 Recall/NDCG | 评测代码（**第 5 周你要自己写一份**） |

### 1.3 边界

- 它**不能**帮你训练生成式推荐模型（第 5 周那个 T5 式模型要自己写）。
- 但第 5 周它仍然有用：**它是你的对照组生成器**。你改协议、加子集评测时，随时能用它重跑一份判别式基线。
- 它的默认配置写在 `recbole/properties/` 下（`overall.yaml` / `dataset/sample.yaml` / `model/SASRec.yaml`），我们的 yaml 只需要写「与默认不同的部分」，但**报告里贴的是合并后的最终配置**（RecBole 会打进日志的 `Final args` 段）。

## 2. SASRec 的具体流程

**出处**：Kang & McAuley, *Self-Attentive Sequential Recommendation*, ICDM 2018（arXiv:1808.09781）。

**它要解决的问题**：给定用户的历史物品序列，预测下一个最可能交互的物品。

### 2.1 一次前向的完整流程（用 user 0 的真实数字）

| 步 | 操作 | 张量形状 / 真实数值 |
|---|---|---|
| 1 | 取用户历史 item id 序列，保留最近 200 个，**右边**补 0（左对齐） | `[200]`，内容是 `[i₁…i₅₁, 0×149]` |
| 2 | 查物品嵌入表（3417×64）+ 位置嵌入表（200×64），相加 | 两个 `[200, 64]` → 相加 → `[200, 64]` |
| 3 | 2 层因果自注意力（每层：2 头自注意力 + 前馈网络，含残差与 LayerNorm） | `[200, 64]` → `[200, 64]` |
| 4 | 取**最后一个有效位置**（下标 50，即第 51 位；不是下标 199）的向量 | `[64]` |
| 5 | 与 3417 个物品嵌入做矩阵乘 | `[3417]` 个分数 |
| 6 | 标签 = 第 52 个物品，算交叉熵 | 标量 loss |
| 7 | 反传 + Adam 更新参数 | — |

**评测时**：同样出 3417 个分数，把训练集出现过的物品分数置 `-inf`，排序，看目标物品排第几 → Recall@K / NDCG@K。

> **补 0 补在哪边？（已核 RecBole 源码，2026-09-22）**
> `SequentialDataset.data_augmentation()` 先建一个**全 0 张量**，再把真实序列填到 `[:length]` 上 ——
> 也就是**左对齐、右边补 0**，真实物品永远落在前 `length` 位。同时另有一个 `item_length` 字段记录真实长度，
> SASRec 靠它做 mask，所以"最后一个有效位置"是 `length-1`。
> 窗口滑动是 `if i - seq_start > max_len: seq_start += 1`，因此**保留的确实是最近的一段**，窗口长度 ≤ `MAX_ITEM_LIST_LENGTH`。
> （RecBole 官方文档给的示例 `[1,0,0] → 2` 也是右补 0，与源码一致。）

### 2.2 三个必须搞清楚的机制

**① 位置嵌入为什么必要**
自注意力是对所有位置做加权求和，本身**不含顺序信息**——把序列打乱，输出不变。所以必须显式把「第几位」编码成向量加进去。

**② 「因果」（causal）是什么意思**
第 t 个位置只能注意到第 1..t 个位置，看不到 t 之后。做法是在注意力分数矩阵上加一个上三角为 `-inf` 的掩码。**不加就是作弊**——模型会直接看到要预测的答案。

**③ 为什么取「第 51 个位置」而不是「第 200 个」**
因为**右边**补的 149 个 `0` 是填充，不是真实行为。第 51 位才是"用户最后一个真实行为"的位置，它的输出向量才代表用户此刻的兴趣。
（对应 `gather_indexes(output, item_seq_len - 1)`：左对齐时最后有效位置就是 `length-1`。若改成右对齐，这个索引公式要跟着改。）

### 2.3 为什么用自注意力而不是 RNN

| | RNN（GRU4Rec） | 自注意力（SASRec） |
|---|---|---|
| 信息传递路径 | 第 100 位 → 第 1 位要经过 100 次递推 | 任意两位一步直连，路径长度 1 |
| 并行性 | 必须逐时间步串行 | 200 个位置一次矩阵乘算完 |
| 顺序信息 | 隐式编码在递推里 | 必须显式加位置嵌入 |
| 长序列表现 | 距离越远越容易丢信息 | 不受距离影响（代价是 O(n²) 计算量） |

### 2.4 损失函数

**CE（交叉熵）**：把 3417 个分数过 softmax，取正确物品那一项算 `-log(p)`。
这是"**3417 分类问题**"的视角：物品数 = 类别数 = 输出层维度。

RecBole 里还有一个选项 **BPR**（贝叶斯个性化排序，成对损失：只要求正样本分数 > 负样本分数）。
**本项目统一用 CE**，两个基线口径必须一致，否则表里两行不可比。

### 2.5 论文 ML-1M 的超参（供对照）

| 超参 | 论文取值 |
|---|---|
| self-attention block 层数 | 2 |
| 位置嵌入 | 可学习 |
| 嵌入层与预测层 | **共享** item embedding |
| 优化器 / 学习率 | Adam / 0.001 |
| batch size | **128** |
| dropout | **0.2**（ML-1M 专属，其他数据集 0.5） |
| 最大序列长度 | **200** |

> 注意：RecBole 的默认 `train_batch_size` 是 **2048**、dropout 是 0.5，和论文不同。**这不影响我们的实验**——我们锁的是"我们自己的协议"，不是"复现论文"。但**必须记录**：报告里要写你实际用的值。

## 3. GRU4Rec 是什么

**出处**：Hidasi et al., *Session-based Recommendations with Recurrent Neural Networks*, ICLR 2016。

**它要解决的问题**：同一件事——给定物品序列，预测下一个物品。区别在**用什么网络读这个序列**。

**机制**：用 **GRU（Gated Recurrent Unit，门控循环单元）** 逐时间步递推：

```
h_t = f(h_{t-1}, x_t)
```

GRU 内部有两个门：**更新门**（决定旧状态保留多少）和**重置门**（决定旧状态对当前候选状态的影响程度）。最后一个时间步的隐状态 `h_T` 就是用户兴趣向量，再和全部物品点积打分。

**和 SASRec 的差异**（同一份配置、同一个数据管线，只换模型）：

| | SASRec | GRU4Rec |
|---|---|---|
| 读序列的方式 | 自注意力，一次看全部 | GRU，逐时间步递推 |
| 位置编码 | 需要显式加 | 递推本身带顺序 |
| 并行 | 可以 | 不行 |
| 参数量级 | 差不多（hidden 64 量级） | 差不多 |
| 本项目里的角色 | **主基线** | 第二根基线（有余力再跑） |

**为什么顺带跑它**：序列推荐有两条技术路线（RNN 派 vs 注意力派）。只跑 SASRec，你没法回答"是不是只有注意力才有用"。多一根本基线，第 5 周生成式模型的对比表才站得住。

**注意**：GRU4Rec 原论文是**会话级**（session-based，匿名短会话）设定；RecBole 把它实现成了**用户级序列推荐模型**，和 SASRec 共用同一套数据管线——这正是它能直接复用同一份配置文件的原因。

## 4. 论文用的数据集，和我用的是同一个吗？

**结论：是同一个数据集，而且预处理结果能对上；只有评测口径不同。**

### 4.1 逐项对照（已核原文）

| 项目 | SASRec 论文（ML-1M） | 我们 | 一致 |
|---|---|---|---|
| 数据集 | MovieLens-1M（论文还用了 Beauty / Games / Steam） | ml-1m | ✅ |
| 过滤规则 | "discard users and items with fewer than 5 related actions" | 5-core 迭代到收敛 | ✅ |
| 过滤后规模 | 6,040 用户 / 3,416 物品 / 1.0M 交互 | 6040 / 3416 / 999611 | ✅ **完全对上** |
| 划分 | 最后 1 个测试、倒数第 2 个验证、其余训练 | leave-one-out，完全一致 | ✅ |
| 指标 | Hit@10、NDCG@10 | Recall@5/10、NDCG@5/10 | ✅（单测试物品时 Hit@10 = Recall@10） |
| 最大序列长度 | ML-1M 用 **200** | 建议 200 | ✅ |
| **评测候选集** | **1 正 + 100 随机负** | **全部 3416 个物品** | ❌ **唯一差异** |

论文原文（§5.1）：

> "For each user u, we randomly sample 100 negative items, and rank these items with the ground-truth item. Based on the rankings of these 101 items, Hit@10 and NDCG@10 can be evaluated."

### 4.2 论文在 ML-1M 上的数字（已核 Table III）

| 指标 | 数值 | 口径 |
|---|---|---|
| Hit@10 | **0.8245** | 101 个候选 |
| NDCG@10 | **0.5905** | 101 个候选 |

**这两个数字不能拿来和我们的结果比。** 候选集从 101 变成 3417，分母大了 34 倍，同一个模型算出来的 Recall/NDCG 会低一大截。**这是正常现象，不是你的 bug。**

### 4.3 顺带一个更普遍的坑：论文之间搬数字也有风险

TIGER 的论文在附录里明确写了：除了 P5 之外，**所有 baseline 的数字直接取自 S³-Rec 公开的结果**。也就是说，TIGER 表里 SASRec 那一行的数字，是别人论文里的数字——他们各自的划分细节、候选集构造未必完全一致。

**所以「跨论文比数字」这件事本身就要打问号。** 第 5–6 周写对比分析时，这一点必须说清楚。

### 4.4 TIGER 的口径（提前知道，第 5 周要用）

- 划分：leave-one-out（最后 1 个测试、倒数第 2 个验证）——**和我们一样**
- 指标：Recall@5/10、NDCG@5/10——**和我们一样**
- 候选集：全部物品（论文没有"采样负例"的描述；且专门讨论了"生成的 ID 可能不对应库里任何物品"，只有全库匹配时这个问题才存在）
- 训练时历史长度限制：**20**（Amazon 数据集的序列短，和 ML-1M 用 200 是两回事）

## 5. 全量排序现在还能改吗

**能改，而且现在是你唯一的窗口期。**

### 5.1 判断依据

协议只在「**还没有任何模型结果**」时是自由的。

- 现在改 = 只改配置文件里的两行，零损失。
- 跑完 SASRec、结果表填上之后再改 = 前面所有数字作废，全部重跑，而且周报里已经报过的数字要更正。

### 5.2 两条路线的取舍

| | 全量排序（我们） | 采样负例（论文） |
|---|---|---|
| 候选集 | 全部 3416 个物品 | 1 正 + 100 负 |
| 随机性 | 无，完全确定 | 有，换种子数字会变 |
| 跨模型可比性 | 强（候选集固定） | 弱（不同论文采样数不同） |
| 与论文数字可比 | ❌ | ✅ |
| 与生成式模型对齐 | ✅ 天然对齐（生成模型的候选集就是全部合法 ID） | ❌ 无法对齐"采哪些负例" |
| 评测速度 | 慢 | 快 |
| 数字观感 | 低 | 高 |

### 5.3 我的建议：保持全量排序

1. **第 5 周的对比会做不下去。** 生成式模型的输出是"生成一串语义 ID"，候选集天然是全部合法 ID 的集合。没法给它"随机采 100 个负例"。候选集一旦对不上，判别式与生成式就没法放进同一张表——而那张表占 25% 的成绩。
2. **TIGER 用的就是全量口径**（见 §4.4），而它正是你最终要对比的对象。
3. **无随机性 = 可复现性好**，正好对应"结果能够复现"这条考核要求。

**代价必须付**：数字偏低（观感差）、评测更慢。

### 5.4 如果决定改

今天就改，并且同步做三件事：
1. 改 `config/*.yaml` 里的 `eval_args.mode`（`full` → `uni100`）
2. 更新 README 的协议表
3. 在周报里写一句"协议在跑基线之前调整过一次，原因：___"

然后锁死，第 3–7 周不再动。

## 6. 「能复现」是底线，不是上限

### 6.1 对着结项标准看

| 等级 | 标准 | 复现的角色 |
|---|---|---|
| 不合格 | 结果无法复现 / 答辩无法解释自己的实现 | **复现是红线** |
| 合格 | 跑通第一至第三阶段，指标合理，非法生成率近零 | 复现是入场券 |
| 优秀 | 完成第四阶段改进探索 + 消融且分析有深度；或工程质量突出、实验设计严谨 | 复现只是前提，不是加分项 |

**把 RecBole 的 SASRec 用默认参数跑出来填进表格 = 合格，不是优秀。**

### 6.2 复现的真正意义：测量工具的校准

工具不准（协议不统一、种子没固定、候选集不一样），后面所有对比都是噪声：

> 你改了一个超参，指标涨了 0.003。是改动有效，还是随机波动？

没有干净的基线，这个问题永远回答不了。

### 6.3 三层目标

| 层次 | 目标 | 达标意味着 |
|---|---|---|
| 底线（合格） | 跑通 + 可复现 | 你的数字**可信** |
| 目标（良好） | 同一协议下的完整对比表 + 冷启动/长尾分组分析 | 你的数字**有信息量** |
| 优秀 | 一项改进 + 消融 + 归因分析 | 你的数字能**回答问题** |

**先拿入场券，再谈奖杯。**

## 7. SASRec vs TIGER：判别式 vs 生成式

### 7.1 先澄清一个常见误解：SASRec 不是「召回重排」那套架构

工业界搜广推的漏斗是一套**工程架构**，不是某个模型：

```
百万级物品
  ↓ 召回      双塔 + 向量检索（ANN），降到几千
  ↓ 粗排      轻量模型，降到几百
  ↓ 精排      重模型，降到几十
  ↓ 重排      多样性打散 / 业务规则
  ↓ 展示
```

SASRec 是**一个模型**，不是这套架构。它的输入是用户行为序列，输出是「下一个物品」的概率分布。三点必须分清：

1. **学术评测根本不分层。** SASRec 论文的评测就是一次全量 softmax 排序，没有召回 / 粗排 / 精排 / 重排。
2. **SASRec 塞进工业漏斗的话，通常落在精排**（或作为召回的一路分支）。因为它的输出层是「物品数」维，物品上百万时这一步算不动。
3. **工业召回的主流做法是双塔 + ANN 检索**，不是 SASRec。双塔把用户和物品各编码成一个向量，再用近似最近邻在百万候选里快速筛。

而 **TIGER 恰恰是把召回和排序合并了** —— 它用生成的方式直接产出候选，论文的卖点之一就是端到端，不需要分开的召回 + 排序两段。（旁证：TIGER 论文的对照方法里，除 P5 外基本都是双塔 + ANN 方案。）

### 7.2 逐项对比

| 维度 | SASRec（判别式） | TIGER（生成式） |
|---|---|---|
| 出处 | Kang & McAuley, ICDM 2018（arXiv:1808.09781） | Rajput et al., NeurIPS 2023（arXiv:2305.05065） |
| 一句话 | 从固定集合里**挑**一个 | 一个 token 一个 token **生成**出来 |
| 物品表示 | 可学习的 embedding（每个物品一个向量，从交互里学） | 3 个语义 ID token（由文本导出，不学） |
| 语义来源 | 无 —— 纯靠共现学 | 预训练文本编码器 + RQ-VAE |
| 输出层维度 | **物品数**（我们这里 3416） | **码本大小**（256 量级）—— 与物品数无关 |
| 序列建模 | 因果自注意力（单向 Transformer） | T5 式 encoder-decoder |
| 得到答案的方式 | 一次前向，取最大 | 自回归 3 步 + beam search |
| 约束解码 | 不需要 | **需要**（前缀匹配 / Trie 剪枝） |
| 冷启动物品 | ❌ 不行 —— 新物品没有训过的 embedding | ✅ 可以 —— 有文本就能算出语义 ID |
| 参数量 | 小（hidden 64 量级，约百万） | 论文实现约 13M；我们计划用 T5-small 量级（约 60M） |
| 训练 / 推理成本 | 低 | 高（自回归 + beam） |
| 物品数增大时 | 输出层线性膨胀 | 输出层固定不变 |
| 本项目角色 | **主基线（第 2 周）** | **主角（第 3–6 周）** |

### 7.3 三个必须理解的点

**① 输出层维度不同，这是最本质的差别。**
SASRec 学的是「物品 i 和物品 j 有多像」，靠的是它们在同一个用户序列里共现。
TIGER 学的是「这个 token 后面该接哪个 token」，物品的相似性**来自文本**，不来自共现。

**② 为什么 TIGER 需要约束解码。**
SASRec 的输出天然合法 —— 3416 个候选都是真实物品。
TIGER 的输出空间是 `256³ ≈ 1677 万` 种组合，而真实物品只有 3416 个，**绝大多数组合不对应任何物品**。
所以要在每一步只允许「能通向某个真实 ID」的 token，把非法路径剪掉（前缀匹配 / Trie）。
论文专门报了一个指标叫**非法生成率**（invalid generation rate），目标是接近 0。

**③ 语义 ID 撞车了怎么办。**
RQ-VAE 是"找最近的码字"这种量化，两部电影完全可能落到同一组码字。TIGER 的做法是**在末尾追加一个自增序号**：
两个物品都落到 `(10,24,52)`，就分别记成 `(10,24,52,0)` 和 `(10,24,52,1)`，语义 ID 从 3 元组变成 4 元组。
这样反查表仍然一一对应。

> 这条直接对应我们第 3–4 周的**码本质量分析**：要统计「3416 部电影映射出了多少组不同的语义 ID」。
> 撞车数量就是必须补的自增位数，也是码本塌缩的量化指标。

### 7.4 一句话总结

SASRec 的输出是「在 3416 个类别上做一次分类」；TIGER 的输出是「生成 3 个 token 组成的序列」。这就是两种范式的全部差别。

两者的结果可以放进同一张表 —— 前提是协议一致（同一份数据、同一个划分、同一个候选集、同一套指标）。这正是第 2 周要把协议钉死的原因。

### 7.5 TIGER 的实现细节（第 3–4 周要用，先记着）

| 项 | 论文取值 |
|---|---|
| 文本编码器 | Sentence-T5，输出 768 维 |
| 文本拼装 | title + price + brand + category 拼成一句 |
| RQ-VAE 编码器 | MLP 512 → 256 → 128 |
| 码本 | 3 层，每层一个 `256 × 32` 的码本（**每层独立，不共享**） |
| 损失权重 β | 0.25 |
| 码本初始化 | 用 k-means 聚类中心（防码本塌缩的关键手段） |
| RQ-VAE 训练 | 20k epoch，要求码本使用率 ≥ 80%；Adagrad，batch 1024 |
| 语义 ID 长度 | 3（撞车时补第 4 位自增序号） |
| 序列模型 | T5X encoder-decoder，约 13M 参数 |
| 序列模型训练 | batch 256，100k–200k steps |
| 用户表示 | 用户 id 哈希到 2000 个 token，拼在行为序列前面 |
| 训练时历史长度 | 限制 20（Amazon 数据序列短；ML-1M 我们用 200） |
