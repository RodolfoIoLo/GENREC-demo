## 1. Motivation

### 1.1 传统的召回方案存在什么问题?

召回模块是搜推系统的先驱,其目标是从候选集中快速,粗鲁地筛选出一个能够涵盖用户需求的集合,提供给后续的排序模块.

由于有排序模块把关,因此召回模块不苛求准确,而是尽可能"应召尽召",避免漏召可能满足用户需求的Item.

传统的召回方案往往通过"双塔"范式来缓解海量候选带来的性能压力.

*何为双塔范式*?

双塔,顾名思义,两个互相独立的塔,双塔的参数是不共享的

- QU Tower: 输入 = 用户特征 + 当前查询(User + Query), 输出 = 一个向量, 即QU emb
- Item Tower: 输入 = 物品特征(ID, 类目, 标题文本等), 输出 = 一组向量, 即Item emb的集合

ANN 检索(Approximate Nearest Neighbor,近似最近邻搜索)​ ---- 给定一个查询向量,在一个巨大的向量集合里找出距离最近的若干个.之所以要"近似",是因为 Item 有千万个,逐个算距离就退回了原问题.ANN 用索引结构(HNSW,IVF-PQ 这类)把搜索加速,代价是结果不保证是真正最近的.

*那么双塔范式存在什么问题呢?*

1. 建模目标的不一致,召回模型通常通过负采样的方式来训练一个"打分函数",这个模型训练目标无论与实际目标的物理含义还是后续排序模块的目标均存在明显的不一致.
2. 该范式将QU及Item两侧的信息压缩成一个固定且低维的向量中,这个向量可能无法充分编码复杂的信息,成为整个召回系统的"瓶颈"所在.
3. 从模型的结构设计就可以明显看出,双塔之间直至最后的emb检索阶段才有一定交互,此时信息已经被高度抽象压缩,信息交互的作用有限,该范式不支持两侧的交叉特征,双塔之间缺乏信息的深度交互,这就在极大程度上限制了模型的表征能力.

> 关于第一点,双塔的训练阶段:批内负采样
>
> 双塔的训练标准是批内负采样,即把一个batch内的其他样本的物品,直接当作当前用户的负采样
>
> 假设一个batch有B个样本,每个样本是用户u与其真实交互过的物品i,整个batch的前向是:
>
> 1. 用户塔对这B个用户各算一个向量 -> 矩阵U, 形状(B, d)(B:batch d:dimension)
> 2. 物品塔对这B个物品各算一个向量 -> 矩阵V, 形状(B, d)
> 3. 计算U与V的点积矩阵,形状(B, B),第i行第j列是用户u_i与物品v_j的相似度
>
> 训练阶段的批内负采样此时简单地认为,只有矩阵的对角线上的元素是正样本,其他都是负样本,即用户u_i与物品v_j(i!=j)没有交互过,所以是负样本
>
> 得到点积矩阵之后,损失对每一行做softmax交叉熵,要让对角线那个位置最大,这意味着梯度会同时落到两个塔上,用户塔参数的梯度里含有V,物品塔参数的梯度里含有U,所以一个batch的前向必须两边同时在场
>
> 在这一轮前向之后,要做的当然就是反向传播+不断循环啦

### 1.2 为什么会诞生生成式的召回方案?

"双塔"范式由于其模型训练与检索两阶段分离的设计模式,严重限制了其"天花板"

召回二阶段范式向一阶段范式的演化,由于召回模型与排序不同,它不需要对每个Item均作出严格准确的预估,从而保障排序的精准度,它只需要生成一个相对粗糙,但可以Cover用户需求的最优集合即可,这就非常契合生成式范式的做法.那么剩下的问题,就是如何将生成式,也就是Transformer的基础建模范式应用到召回领域?众所周知,Transformer建模的核心是通过一组Token序列进行编码,通过next token预估的方式,生成序列接下来最可能的Token.这种方式与搜推系统经典的序列建模范式又非常相像,而本文介绍的Tiger也正是沿着序列建模的路径所提出的创造性的生成式序列建模方案.

所谓序列建模,主要源于一个纯粹的思想:直接学习用户行为序列中蕴含的"下一个物品"的分布.其目标是学习概率分布,通过编码用户行为序列的信息,来预估下一个用户最可能交互的Item.经典的做法包括GRU4REC,AttRec,SASRec,BERT4Rec,P5等,论文也是与这些做法一一进行了对比.

其中,早在SASRec这篇工作中,就已经将self-attention的结构应用到了序列建模中.那么,同样是基于Transformer的next token预估范式,通过编码用户的行为序列信息来预估下一个可能交互的Item,本文提出的Tiger与SASRec又有什么区别呢?个人认为主要在于以下两个点:

1. 首先,SASRec是以系统候选库为基础,对候选集进行打分,从中挑选与用户交互概率最大的Item.也就是说它虽然用的是生成式的模型范式,但做的实际还是判别式的任务,而非"从无到有"的生成式任务,Transformer结构只是升级了一下模型的表征能力罢了.更何况,在召回模块,SASRec同样无法规避海量候选带来的巨大性能压力,因此业界的普遍做法是把它作为一个建模序列特征的中间模块,最终成为"双塔"范式QU Tower的一部分,因此完全没有实现范式层面的突破.
2. 另外更重要的一点是,SASRec对序列依旧采用传统的embedding建模方法,而Tiger则是创造性地提出了一种语义ID的思想,通过建模Item的内容语义来构建Token序列,从语义层面进行预估.不仅大大提升了模型的泛化性,还在新品冷启这个长时间困扰推荐系统的棘手问题上取得了突出的表现.

## 2. 语义ID思想

由于Transformer是基于token序列进行预测,那么如何构建token序列就成为生成式建模的关键.传统搜推系统中,Item ID通常基于Item embedding的思想被表示为一个低维连续向量,而这个向量中的值不仅连续,且没有明确的物理含义,因此显然不能直接作为token使用.到这里,可能有人会问了,那直接使用原始的离散Item ID可行吗?答案同样是否定的.

首先,最重要的一点,这个Item ID是随机赋予的,没有任何物理含义,比如三个Item,*"品牌X的橘色鞋子","品牌Y的红色鞋子"和"品牌Y的橘色鞋子"*从直觉上明显相近,但是由于Item ID的随机性,其Item ID之间看起来没有任何关联,那么通过"品牌X的橘色鞋子","品牌Y的红色鞋子"组成的序列,显然是很难生成出"品牌Y的橘色鞋子"这样的结果的,生成式建模正是奠基在内容语义的理解之上.其次,由于候选库庞大的数量级,Item ID的往往比较长,而Transformer的推理是串行的模式,其推理时间会随着序列长度的变长而显著上涨,这就带来了较大的性能及成本压力.

语义ID是什么呢?简单来说就是通过一种离散编码的方式,将Item Embedding编码成由几个离散数字组成的元组.

这其中的优势是很明显的

1. 编码带有清晰的语义信息,相似的Item对应的编码也是相似的,这样就更有利于模型基于语义,学习Item之间的关联,从而大大提升模型的泛化性.
2. 这种基于语义的生成方式也能从很大程度上规避搜推领域常见的"马太效应"问题,对新品更加友好.
3. 编码元组的各个元素之间有明确的层次关系,以图3为例,元组的三位分别代表类目,品牌和颜色,不仅更有利于模型学习Item之间的复杂关系,也为系统提供了更强的可解释性.
4. 可以用较小的成本存储海量的候选,假设语义ID包含M个元素,每个元素有K种选择.那么,在只需要存储M*K个语义ID编码的情况下,理论上最多可以表示K^M个Item.同时,相比Item ID,语义ID的长度明显更短,大大缓解了性能压力.

## 3. TIGER算法原理与细节

TIGER的原理已经非常清楚了:首先对每个Item生成对应的语义ID,再基于用户交互过的Item序列对应的语义ID序列进行Transformer的自回归生成,预测下一个用户可能交互的Item.

### 3.1 语义ID生成

语义ID生成,简单来说,就是
- **将Item的特征输入一个预训练好的文本Encoder进行编码,拿到对应的item embedding**,
- **再通过一定的离散编码手段将高维连续的item embedding转化成低维离散的Semantic ID(语义标识符)**.

#### 语义特征的选取

众所周知,传统的搜推系统为了充分建模用户的个性化偏好,会大量使用与用户交互强相关的数值,统计类特征,例如一定时间窗口内的点击率,转化率,商品的整体销量,视频的平均播放时长等.但Tiger基本放弃了这些特征

至于为什么:
1. 传统搜推建模的就是用户与Item的交互关系及用户的个性化偏好,这类特征能很好地描绘这一点,而以Tiger为代表的生成式搜推思想是以内容语义的理解,泛化为核心的建模思想,因此这类缺乏语义信息的数值,统计类特征起到的作用非常有限.
2. 另外很重要的一点是,与传统搜推特征emb伴随模型训练不断更新不同,生成式思想对应的语义ID在生成完成后到后续整个推理模型训练阶段是固定不动的,而数值统计类特征会随时间不断发生变化,显然与该要求不符.

所以TIGER对于特征的选取原则显而易见了:蕴含很强的关于物品本身的语义信息,不随时间发生变化的静态特征,for example:"Item本身的ID,标题,品牌,描述信息,类目等,或者通过其他深度学习模型生成的静态视觉,多模态特征等,均能够满足语义ID生成的需求."

#### 语义特征的产生

*`物品 -> (文本编码器) -> 一个768维的向量 -> (Encoder) -> (RQVAE) -> 一个离散的语义ID(k_1, k_2, k_3)`*

用于编码特征的Encoder通常选用常见的文本编码器,例如Sentence-T5,BERT,论文中对这一部分的编码一笔带过,但是可以想象这里的item embedding会是决定后续效果的关键一环

得到item embedding之后,当然需要进行离散编码了,得到语义标识符

--- 

而TIGER的离散编码方式是**RQVAE**

什么是RQVAE呢?

其核心执行逻辑:

1. 首先定义一个规模为K的码本为C = {e_1, e_2, ..., e_K},其中每个e_i都是一个d维向量,也就是码本的大小为K,每个码字的维度为d,Encoder输出的隐变量z是一个d维向量
2. 将残差向量初始化为r_0 = z,从码本C中,找到距离r_0最近的码本向量索引k_1以及向量值e_k_1,同时将残差向量更新为r_1 = r_0 - e_k_1
3. 然后继续对r_1执行上述操作,循环执行,直至到达提前规定好的迭代论述N为止

物品文本(title/price/brand/category) -> 文本编码器(如Sentence-T5)(冻结) - > x:768维向量

```
-> Encoder 768 -> 512 -> 256 -> 128 -> 32 -> z

-> 残差量化 -> (k_1, k_2, k_3)

-> Decoder 32 -> 128 -> 256 -> 512 -> 768 -> x̂
```

训练时Encoder和Decoder同时存在,Decoder的唯一作用是把量化之后的向量还原成768维,逼Encoder别把信息丢光,给物品发完 ID 之后,Decoder 就用不上了 ---- 所以这张图的上半部分(编码+量化)才是要长期保留的部分.

### 3.2 自回归预估

语义ID生成后即冻结,在自回归模型的训练过程中不再发生变化,最后的预估基于用户历史交互过的Item序列,通过生成好的语义ID序列来表征(展开).此外,TIGER还尝试引入user id token来表征个性化信息,共分配了2000个可选token,作为序列的第一位,构建完整的token序列,接下来的事情,就是常规的Transformer预估了
